# Design note (written before pipeline code)

Date: 2026-11-03. Inputs: the brief, the [data profile](data_profile.md), and the variable
availability research done in the Explorer. Section 9 lists where the final build diverged.

## 1. Goal in one sentence

Turn two GSS Data Explorer extracts into a queryable, respondent-grain dataset on religiosity
and media consumption, in which every value is either a readable answer or an explicit,
typed reason for its absence, and which a new analyst can extend with another GSS variable by
editing metadata rather than SQL.

## 2. Grain and keys

| table family | grain | key |
|---|---|---|
| raw extract rows | one row per **extract x respondent** | `(extract_name, year, id_)` |
| modelled responses (long) | one row per **respondent x variable** | `(respondent_key, variable_name)` |
| respondent mart (wide) | one row per **respondent** | `respondent_key` |

A respondent is identified by **`(year, id_)`**. `id_` restarts at 1 every survey year (profile
section 2), so `id_` alone is not unique across years. `respondent_key` is the string
`'<year>-<id_>'`, derived, never trusted from the source. Both cuts contain all of 2018; the
raw layer keeps both copies (raw is "as received"), and deduplication is a downstream
transformation that asserts the copies are identical before keeping one.

## 3. Layers

```
source/data/raw/*.json            as received (git, sha256 manifest)
        |  Python loader: validate, type-check schema, load
raw.*            (DuckDB)         row-per-extract-row, original JSON preserved as a JSON column
        |  dbt
staging.stg_gss__*   (views)      unpivot JSON -> long rows, light typing, no business logic
intermediate.int_gss__* (tables)  dedupe across cuts, label -> code via seeds, missing-value
                                  classification, variable-year validity, derived groupings
marts.fct_* / dim_*  (tables)     analyst-facing: long response fact + wide respondent table
analyses/            (SQL)        the six questions + overlap audit
```

Why these layers:

- **raw** exists so re-running or reloading never destroys what was received, and so the
  modelled layer can be rebuilt from inside the warehouse without re-reading files.
- **staging** is a thin typed view so that the "schema" of the extract (which variables exist)
  is *not* written into SQL. The loader stores each row as a JSON object; staging unpivots it
  generically into `(respondent, variable_name, raw_value)`. Adding a variable to a future
  extract needs no staging change.
- **intermediate** is where the survey-specific logic lives, once, in long form: label to code
  lookup, classification into answer / did-not-apply / don't-know / no-answer /
  not-asked-this-year, and the variable-year validity override. Long form keeps this logic
  independent of the number of variables.
- **marts** give analysts what they expect: a long fact for generic aggregation and a wide,
  one-row-per-respondent table generated by a macro from the variable seed (so the wide table
  also grows by editing metadata).

## 4. Database: DuckDB

Chosen because it is dbt-supported (`dbt-duckdb`), embedded (one file, no server, no
credentials, runs on a clean laptop with `pip install`), columnar and analytical (the
`EXPLAIN ANALYZE` plans are meaningful for section 3.2), and reads JSON natively.

Considered and rejected:

- **PostgreSQL in Docker**: fully capable, but a server, a volume, a password and a healthcheck
  for 9,247 rows is disproportionate. The project keeps the raw layer and dbt adapter-agnostic
  so swapping to Postgres is a profile change plus the loader's connection line.
- **SQLite**: no first-class dbt adapter, weak analytical SQL (no `QUALIFY`, limited window
  support), slow unpivots.
- **BigQuery / Snowflake / Athena**: paid or cloud-only; the brief requires a local core.
  They are the right answer at the 75,700 x 7,000 scale and the report's production sketch says so.

## 5. Missing-value semantics

Each cell of the long fact carries three things: `value_code` (numeric GSS code, NULL for
reserved), `value_label` (readable text, NULL for reserved) and `value_status`, one of

| value_status | source code | meaning |
|---|---|---|
| `answer` | >= 0 | genuine response |
| `did_not_apply` | -100 `.i` | skip pattern or respondent not on the ballot carrying the item |
| `dont_know` | -98 `.d` | asked, could not answer |
| `no_answer` | -99 `.n`, -97 `.s`, -90 `.r` | asked, no usable answer (`.s` kept as `missing_detail = skipped_web`) |
| `not_asked_in_year` | -70 `.y` **or** validity seed says the variable was not fielded that year | the instrument did not include the item |
| `uncodable` | -95 `.u` | answer could not be coded |

The validity override matters because the source encodes "not fielded this year" as `.i`
for `relitenv`/`relitennv` in 2016/2018 but as `.y` for `postlife`/`reliten` in 2021 (profile
section 3). The pipeline trusts the **metadata** for "not asked in year" and tests that the
source agrees where it can.

## 6. Semantic metadata (dbt seeds, version-controlled)

| seed | one row per | content |
|---|---|---|
| `seed_gss__variables` | variable | label, question wording, value type (categorical / count / weight / identifier), topic, whether it is modelled, which brief question it serves |
| `seed_gss__code_labels` | variable x substantive code | code, label, optional `group_label` for coarse groupings (relig16 families) |
| `seed_gss__reserved_codes` | reserved code | code, label, `value_status`, `missing_detail` |
| `seed_gss__variable_years` | variable x survey year | coverage: `full`, `ballot` (with which ballots), `none`; source of truth for `not_asked_in_year` |
| `seed_gss__indus10_sectors` | Census industry code range | sector name (NAICS 2007 sector roll-up) for Q3 |

Code lists are generated from the extracts' embedded `codes` metadata by a script, then
committed. Validity and sectors are hand-curated from the Explorer's variable pages and the
Census industry classification. Models read these seeds; no SQL repeats a code or label.

## 7. Loader (Python) behaviour

- Reads only `post_processing_output.json` (the valid JSON). Validates: JSON parses; `data`
  columns all have the same length; required key columns `year`, `id_` present and non-null;
  `year` matches the extract's declared years; `(year, id_)` unique within the extract; every
  column is either in the expected variable list or is logged as an **unexpected column**
  (cut B's `prayer`); values are strings/ints/floats only.
- Idempotent by construction: each extract is loaded in one transaction that deletes that
  extract's rows and reinserts them (`extract_name` is part of the key). Loading A then B, or
  B then A, or A twice yields the same table, which a test proves by checksum.
- Every run writes a row to `raw.load_runs` (extract, file sha256, rows read, rows loaded,
  unexpected columns, validation outcome, started/finished) and structured logs to `logs/`.
- Bad input policy: a malformed file or a key violation fails the load for that extract and
  rolls back; unexpected columns are loaded (they sit in the JSON) and reported; unexpected
  labels (not in the code list) are loaded raw and surface in dbt as `value_status = 'unmapped'`,
  which a test fails on.

## 8. Assumptions

1. `(year, id_)` is unique within a survey year and stable across extracts (verified for 2018).
2. The labels exported by the Explorer are the canonical labels in its code list, so
   label -> code is a lookup, not fuzzy matching (verified: 0 unmapped labels in the profile).
3. The Explorer's reserved codes are the only non-answers; no sentinel like 999 hides in a
   continuous variable (verified: `age`, `tvhours`, `wwwhr` have only numeric or labelled endpoints).
4. Weights: `wtssps` (post-stratified, all years) is the analysis weight; `wtssnrps` carried
   for comparison. Weighted estimates are only ever compared within the same weight.
5. Ballot assignment is random, so ballot-limited items are unbiased on their subset.
6. 2021's mode change (web) is a caveat on trends, not something the pipeline can correct.
7. Extracts are small enough to be reprocessed fully; no incremental logic is needed yet.

## 9. Divergence log (filled in as the build proceeds)

| design said | final build | why |
|---|---|---|
| all staging models are views | `stg_gss__responses` is a table | it is the most expensive query in the project and has two consumers; measured in [query_plans.md](query_plans.md) |
| coarse groupings (`group_label`) live in `seed_gss__code_labels` | separate seed `seed_gss__answer_groups` | `seed_gss__code_labels` is generated from the extracts and regenerating it would wipe hand-curated columns; a separate hand-curated seed keeps generated and curated metadata apart |
| wide mart emits `_label`, `_code`, `_status` per categorical variable | also `_group`, but only for variables that have rows in `seed_gss__answer_groups` | avoids 20 redundant columns that would just repeat the label |
| loader rejects unexpected columns | loader loads them, logs a warning and records them in `raw.load_runs`; the dbt layer leaves them out of the marts via `is_modelled = false` | cut B arrived with an extra column (`prayer`); raw must preserve what was received, and a hard failure would have blocked the whole load for a harmless surprise |
| seeds loaded with `dbt seed` | seeds loaded with `dbt build --select resource_type:seed` | so the seed tests (uniqueness of codes, closed vocabularies) run before any model depends on them |
| "not asked that year" derived from metadata, source `.y` as a check | as designed, and the check found the inconsistency predicted in the profile: `relitenv`/`relitennv` are `.i` in 2016/2018 | kept; `missing_detail = not_fielded_per_metadata` records that the override happened |
