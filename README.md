# GSS religiosity and media consumption pipeline

A small, production-minded pipeline over two extracts of the General Social Survey (GSS):
a Python loader into DuckDB, a dbt project that turns survey codes into analysis-ready models with
explicit missing-value semantics, the analytical SQL for the assignment's questions, and the
documentation of every decision. Built for the Yaqeen Institute data engineering assignment.

**Data source and citation.** The General Social Survey (GSS) is a project of the independent
research organization NORC at the University of Chicago, with principal funding from the National
Science Foundation. The data in this repository were obtained from the GSS Data Explorer and are

## Quick start

Requirements: [uv](https://docs.astral.sh/uv/) (installs the pinned Python 3.12 and every
dependency from `uv.lock`), `make`, and `shasum`. No cloud services, no credentials.

```bash
make setup        # pinned virtualenv + dbt packages
make verify-raw   # SHA-256 check of the committed extracts
make pipeline     # load -> seed (+seed tests) -> build (models + tests) -> analyses -> docs
make test-python  # loader tests: idempotency, load order, bad input (12 tests)
make serve-docs   # dbt documentation site
```

`make pipeline` takes about 20 seconds and leaves behind `data/gss.duckdb`, `logs/`,
`docs/analysis_results/*.md` (the answers to the questions) and `dbt/target/` (dbt artefacts,
docs site). Every step is idempotent; run it again and nothing duplicates.

With Docker instead of uv: `make docker-build && make docker-run`. The image pins the same
`uv.lock`. (Note: the Docker path was written but could not be executed on the development
machine because the Docker daemon was unavailable; the uv path is the tested one.)

Configuration is by environment variables with working defaults; copy `.env.example` to `.env`
to change the database path, log location or dbt target. Nothing secret is needed for DuckDB.

## How the pipeline works

```
source/data/raw/*/post_processing_output.json
   | python -m source.pipeline.load_extracts   validate (shape, keys, declared years, scalar values,
   |                                            unexpected columns) and load in one transaction per extract
raw.extract_rows / extract_variables / extract_codes / load_runs      (DuckDB, JSON preserved)
   | dbt build --select resource_type:seed     metadata seeds + their tests
   | dbt build                                 staging (unpivot JSON generically) -> intermediate
   |                                            (dedupe overlap, label->code, missing-value classification,
   |                                            validity by year) -> marts (long fact, wide respondent table,
   |                                            variable catalogue), with 101 tests
   | python -m source.pipeline.run_analyses    runs dbt/analyses/*.sql, writes docs/analysis_results/
   | dbt docs generate
```

Steps run in that order and the runner stops at the first failure (`logs/last_run.json` names
the failing step; `logs/pipeline.jsonl` has every event; `raw.load_runs` has every load attempt
with file hashes and validation findings; `dbt/target/run_results.json` has every model and
test outcome). Re-running after a fix is safe: `make pipeline` again, or
`uv run python -m source.pipeline.run --from build` to skip the load.

## Running the tests

| what | command | count |
|---|---|---|
| loader: idempotency, order independence, overlap identity, bad input | `make test-python` | 12 |
| dbt: seed tests (code uniqueness, closed vocabularies, relationships) | `make seed` | 31 |
| dbt: model tests (keys, accepted values, ranges, relationships, 8 singular expectations) | `make build` | 70 |
| lint: ruff and sqlfluff | `make lint` | |

## Reproducing the extracts

Built in the GSS Data Explorer (free account) on 2026-11-03. Variables (25, identical for both
cuts): `id_`, `ballot`, `year` (added by the Explorer), `wrkstat`, `evwork`, `degree`, `indus10`,
`satjob`, `postlife`, `pray`, `relig16`, `relig`, `attend`, `reliten`, `relitenv`, `relitennv`,
`news`, `tvhours`, `wwwhr`, `inttech`, `age`, `sex`, `region`, `wtssps`, `wtssnrps`.

1. Explore GSS Data > Search GSS Variables; open each variable and click **Add to Extract**.
2. MyGSS > Extracts > **Create Extract**. Name it `gss_cut_a_2016_2018`.
3. Build Extract: **Add all variables** from the cart. Case Selection: drag `year` in and tick
   **2016** and **2018** only.
4. Choose output options: Years Included = 2016, 2018; formats **JSON**, DDI 3.1 Metadata,
   Excel (metadata only). Create, wait for *Completed*, download.
5. Repeat as `gss_cut_b_2018_2021` with **2018** and **2021**.
6. Unzip; the files under `batch_0/result/` are what is committed in `source/data/raw/<cut>/`.

Expected: cut A 5,215 rows (2,867 + 2,348), cut B 6,380 rows (2,348 + 4,032), overlap 2,348,
distinct 9,247. Cut B carries an extra `prayer` column that was left in the cart by mistake; it is
kept as received and documented, not modelled. Extracts are deleted from the Explorer after 14
days, which is why the files are committed.

## Where to look for the answers

`docs/analysis_results/` holds one Markdown table per question, regenerated on every run, and the
report's "Results and caveats" section discusses them. The SQL is in `dbt/analyses/`.
